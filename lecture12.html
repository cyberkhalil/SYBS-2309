ما هو إطار العمل ولماذا Flask

إطار العمل (Framework) هو مجموعة من الأدوات والقواعد الجاهزة التي تختصر عليك بناء الجزء المتكرر من التطبيق: استقبال الطلبات، توجيهها إلى الكود المناسب، تحليل البيانات، إعداد الاستجابة، والتعامل مع الأخطاء. بدونه، ستكتب هذه الحلقة بنفسك من الصفر في كل مشروع. معه، تبدأ من حيث يجب أن تبدأ: منطق تطبيقك.

Flask (على الخادم)

يستقبل الطلب، يوجّهه إلى def about() في Python، ثم يرسل ما ترجعه الدالة.

Flask — إطار خفيف

  • صغير، مرن، وقليل "الرأي"
  • تختار فيه ما تحتاجه فقط
  • مناسب للتعلّم والمشاريع الصغيرة
  • مثالي للمحاضرات والمختبرات

Django — إطار كامل

  • يوفّر كل شيء جاهزاً (ORM، admin، auth)
  • يعطي بنية أكبر وأكثر تنظيماً
  • مناسب للمشاريع الكبيرة
  • منحنى تعلّم أعلى

اخترنا Flask لأن هدفنا في هذا المساق هو فهم المفاهيم: طلب، مسار، استجابة، قالب، نموذج، جلسة، تصحيح. لا لأن نغرق في بنية إطار ضخم. حين تفهم هذه المفاهيم في Flask، يمكنك لاحقاً الانتقال إلى Django أو FastAPI بسهولة، لأن المبادئ نفسها.

فكرة جذرية بسيطة: Flask ليس سحراً. هو مكتبة Python تنتظر على منفذ (غالباً 5000)، وتستقبل طلبات HTTP، وتبحث في جدول مساراتك لتعرف الدالة المناسبة، ثم تنفّذها وتُرجع ناتجها. إذا فهمت ذلك، فأنت تفهم 80% من Flask.

أول تطبيق Flask

الآن نكتب أول تطبيق. اسم الملف مهم: سنسميه app.py أو main.py. Flask يحتاج أن يعرف نقطة البداية. سنستخدم النمط القياسي مع if __name__ == "__main__".

app.py — أول تطبيق PYTHON 
# app.py — أول تطبيق Flask
from flask import Flask

# إنشاء كائن التطبيق
app = Flask(__name__)


# تعريف مسار "الجذر"
@app.route("/")
def home():
    return "مرحباً بك في أول تطبيق Flask!"


# تشغيل الخادم عند تنفيذ الملف مباشرة
if __name__ == "__main__":
    app.run(debug=True)

شغّل الملف بأحد أمرين. الطريقة الأولى عبر Python مباشرة، والثانية عبر أمر Flask.

تشغيل التطبيق SHELL 
# الطريقة الأولى
python app.py

# الطريقة الثانية (تستخدم متغير FLASK_APP)
# Windows
set FLASK_APP=app.py
flask run
# macOS / Linux
export FLASK_APP=app.py
flask run

# سترى في الطرفية:
#  * Running on http://127.0.0.1:5000

افتح المتصفح على http://127.0.0.1:5000. سترى النص: "مرحباً بك في أول تطبيق Flask!". مبروك — هذا تطبيق ويب حقيقي، يعمل على خادم محلي، يستقبل طلباً ويرد عليه. كل ما أضفناه هو ملف Python من 10 أسطر.

Flask(__name__)

  • ينشئ كائن التطبيق
  • __name__ يحدد اسم الحزمة
  • يعتمد عليه Flask للعثور على القوالب والملفات
  • لا تغيّر هذا المعامل الآن

@app.route("/")

  • مزخرف يربط المسار بدالة
  • عند زيارة / تُنفَّذ home
  • ناتج الدالة هو نص الاستجابة
  • سنتعلم غداً إرجاع HTML

app.run(debug=True)

  • يشغّل الخادم المحلي
  • debug=True يعطي رسائل مفصلة
  • يعيد التحميل تلقائياً عند التعديل
  • ممنوع في الإنتاج
جرّب الآن: عدّل نص الرد من "مرحباً..." إلى أي شيء آخر، احفظ الملف. لاحظ أن Flask يكتشف التغيير ويعيد التشغيل تلقائياً (لأن debug=True). أعد تحميل الصفحة، وسترى النص الجديد. هذه أول دورة تطوير-تجربة كاملة لك.

المسارات و@app.route

تطبيق Flask واحد يمكن أن يحتوي عشرات المسارات. كل مسار هو عنوان URL يُعادل دالة Python. عند وصول طلب، يبحث Flask عن أول مسار يطابقه، وينفّذ الدالة، ويُرجع ما ترجعه.

app.py — مسارات متعددة PYTHON 
from flask import Flask

app = Flask(__name__)


@app.route("/")
def home():
    return "الصفحة الرئيسية"


@app.route("/about")
def about():
    return "عن المساق: SYBS 2309 — تصميم وبرمجة الويب"


@app.route("/contact")
def contact():
    return "للتواصل: makhalil@ucas.edu.ps"


@app.route("/courses/web")
def web():
    return "صفحة مقرر الويب"


if __name__ == "__main__":
    app.run(debug=True)

افتح الآن: / · /about · /contact · /courses/web. كل عنوان يعرض نصاً مختلفاً من دالة مستقلة. هذا هو الأساس الذي سنبني عليه بقية التطبيق.

مسار ثابت

  • نص ثابت، مثل /about
  • يجب أن يكون فريداً
  • حساس لحالة الحروف في الغالب
  • لا يحتوي معاملات متغيرة

مسار متداخل

  • /courses/web وأخواتها
  • تنظيم منطقي للمحتوى
  • يسهّل التوسع
  • يُستخدم في أي تطبيق حقيقي

أكثر من مسار لدالة

  • يمكن تكرار المزخرف مرة ثانية
  • مفيد لتبادل صيغ عنوان
  • مثال: /home و/index
  • الدالة نفسها، اسمان
خطأ شائع: نسيان / في بداية المسار. @app.route("about") يسبب ValueError. الصواب @app.route("/about"). والنقطة نفسها على المسار الجذر: "/" وليس "".
سؤال للفهم: ماذا يحدث إن طلبت مساراً غير موجود؟ سيرجع Flask خطأ 404 Not Found برسالة افتراضية. لاحقاً سنتعلم كيف نعرض صفحة خطأ مخصصة، لكن الآن اعلم أن 404 ليست مشكلة Flask بل نتيجة طبيعية لعدم وجود المسار.

معاملات URL الديناميكية

كل صفحة بمسار ثابت لا تكفي لتطبيق حقيقي. نحتاج أحياناً أن نمرر أجزاءً من العنوان إلى الدالة. مثلاً /courses/web بدل /courses/python — كلها تشترك في الشكل /courses/<اسم>. Flask يدعم ذلك عبر معاملات URL بين < >.

app.py — معامل بسيط PYTHON 
from flask import Flask

app = Flask(__name__)


@app.route("/hello/<name>")
def hello(name):
    return f"مرحباً {name}!"


@app.route("/course/<slug>")
def course(slug):
    return f"صفحة المقرر: {slug}"


if __name__ == "__main__":
    app.run(debug=True)

جرّب في المتصفح: /hello/sara — سترى "مرحباً sara!". /course/web — سترى "صفحة المقرر: web". اسم المعامل في المسار يجب أن يطابق اسم المعامل في الدالة. لو اختلفا، سيحدث TypeError.

Flask يسمح أيضاً بتحديد نوع المعامل. الافتراضي نص، لكن يمكن جعله عدداً صحيحاً أو عشرياً:

app.py — معامل بنوع محدد PYTHON 
@app.route("/student/<int:student_id>")
def student(student_id):
    return f"رقم الطالب: {student_id}"

# أمثلة أخرى:
# /article/<int:article_id>
# /price/<float:amount>
# /slug/<path:subpath> (يقبل "/")

ميزة النوع: لو زار المستخدم /student/abc (نص بدل رقم)، سيرجع Flask 404 تلقائياً، لأن المسار لا يطابق. هذا يحسّن التحقق الأولي، ويجعل الكود أقصر.

النوع الافتراضي

  • <name> = نص
  • لا يحتوي /
  • يقبل أحرفاً وأرقاماً وشرطات
  • يُستخدم للأسماء والـslugs

الأنواع المدعومة

  • string (افتراضي)
  • int للأعداد
  • float للأرقام العشرية
  • path يقبل شرطة مائلة
  • uuid لمعرّفات UUID

تنبيه أمني

  • المعاملات نص من المستخدم
  • لا تثق بها أبداً
  • تحقق من الصلاحية في الخادم
  • لا تستخدمها في استعلام SQL مباشرة
مبدأ أمني أساسي: ما يأتي من URL نص خارجي. حتى مع نوع int، تحقق في داخل الدالة أن المعرّف موجود فعلاً (مثلاً في قاعدة البيانات). لا تعتمد على القيد النوعي فقط.

طرق HTTP (GET وPOST)

كل طلب HTTP له طريقة. الافتراضي في Flask هو GET، وهو المناسب لصفحات القراءة. أما POST فهو لإرسال بيانات (تسجيل، نموذج، تحديث). نحدد الطريقة في @app.route عبر methods.

app.py — GET وPOST PYTHON 
from flask import Flask, request

app = Flask(__name__)


@app.route("/subscribe", methods=["GET", "POST"])
def subscribe():
    if request.method == "POST":
        # البيانات ستُرسَل لاحقاً من نموذج
        email = request.form.get("email", "")
        return f"تم استلام البريد: {email}"

    # GET: نعرض صفحة بسيطة
    return "أرسل بريدك عبر POST إلى هذا المسار."


if __name__ == "__main__":
    app.run(debug=True)
المحور GET POST
الافتراضي نعم (Flask يستخدمه افتراضياً) لا، يجب تحديده صراحة
البيانات في عنوان URL (query string) في جسم الطلب
يُخزَّن في السجل غالباً نعم غالباً لا
مناسب لـ قراءة، بحث، تصفح تسجيل، تسجيل دخول، إنشاء
قراءة البيانات في Flask request.args request.form
الخطوة التالية: في المحاضرة 13 سنبني نموذج HTML يرسل بيانات POST إلى هذا المسار، وسنستعرضها ونعرضها من جديد في صفحة. الآن يكفي أن تفهم أن methods تحدد ما يقبله المسار، وrequest.method داخل الدالة يخبرك بالطريقة الحالية.
لا ترسل بيانات حساسة عبر GET. كلمات المرور والرموز تُرسل POST مع HTTPS. GET يظهر في عنوان المتصفح وسجلات الخادم، وهذا خطر أمني واضح.

الاستجابات: نص وHTML وقوالب

ناتج الدالة هو ما يراه المتصفح. الشكل الأبسط هو نص، وهو ما فعلناه حتى الآن. لكن تطبيقاً حقيقياً يحتاج HTML. أمامك خياران: نص HTML صريح داخل الدالة، أو قالب Jinja منفصل.

الخيار الأول: HTML داخل الدالة

app.py — HTML مضمّن (للبداية فقط) PYTHON 
@app.route("/html")
def html_demo():
    return """
    <!DOCTYPE html>
    <html lang="ar" dir="rtl">
    <head>
        <meta charset="UTF-8">
        <title>صفحة من Flask</title>
    </head>
    <body>
        <h1>مرحباً من Flask</h1>
        <p>هذا HTML مضمّن داخل دالة Python.</p>
    </body>
    </html>
    """

هذا يعمل، لكنه فوضوي عند تطوير تطبيق حقيقي: نصوص HTML داخل Python، وسوم مبعثرة، وإعادة كتابة القالب نفسه في كل مسار. لهذا أعطتنا Flask engine القوالب Jinja2.

الخيار الثاني: render_template

نضع الملفات في مجلد templates/، ثم نطلب من Flask أن يقرأ القالب ويمرّر له بعض المتغيرات. النتيجة: HTML نظيف في ملفه، ومنطق في ملفه.

الهيكل TREE 
flask-lab12/
├── app.py
└── templates/
    └── home.html
templates/home.html HTML 
<!DOCTYPE html>
<html lang="ar" dir="rtl">
<head>
    <meta charset="UTF-8">
    <title>{{ title }}</title>
</head>
<body>
    <h1>{{ title }}</h1>
    <p>مرحباً {{ name }}، هذا قالب من Jinja2.</p>
</body>
</html>
app.py — استخدام القالب PYTHON 
from flask import Flask, render_template

app = Flask(__name__)


@app.route("/template")
def template_demo():
    return render_template(
        "home.html",
        title="مرحباً من القالب",
        name="سارة"
    )

templates/

  • مجلد افتراضي في Flask
  • يحتوي ملفات .html
  • يُبحث فيه تلقائياً
  • اسم الملف يُمرَّر كسلسلة

{{ متغير }}

  • تعبير Jinja داخل القالب
  • يُستبدل بقيمته قبل العرض
  • مرّرها بـrender_template
  • غالباً نصوص آمنة تلقائياً

أمان القوالب

  • Jinja يهرّب تلقائياً
  • لكن لا تثق بمدخلات المستخدم
  • |safe خطر
  • لا تعرض نص مستخدم بـsafe
لماذا نفصل؟ لأن HTML داخل Python يجعل الكود صعباً في القراءة، ويصعب تحريره، ويخلط المسؤوليات. القوالب المنفصلة تحل كل هذا، وتفتح الباب للوراثة بين القوالب ({% block %}) التي سنراها لاحقاً. اعتمد على render_template منذ البداية.

وضع التصحيح وقراءة الأخطاء

debug=True عند تشغيل التطبيق يوفّر ميزتين مهمتين: إعادة التحميل التلقائي عند تعديل الملفات، وصفحات أخطاء تفصيلية في المتصفح. هذه ميزة لا تقدّر بثمن أثناء التطوير، لكنها ممنوعة في الإنتاج — تكشف تفاصيل قد تكون خطيرة.

التحميل التلقائي

  • تعديل ملف Python يعيد التشغيل
  • لا حاجة لإيقاف وتشغيل
  • تعديل القوالب قد لا يحتاج إعادة تشغيل
  • توفير وقت كبير

Interactive Debugger

  • عند وقوع خطأ في العرض
  • يعرض Traceback كامل
  • يسمح بفتح Console داخل الخطأ
  • فقط في بيئة التطوير

تحذير الإنتاج

  • عطّل debug في الإنتاج
  • لا تنشر رسائل الأخطاء للمستخدم
  • المخترق يستفيد من Traceback
  • سجل الأخطاء في ملف بدلاً
app.py — مثال يسبّب خطأ PYTHON 
@app.route("/broken")
def broken():
    # قسمة على صفر
    return 10 / 0

زُر /broken. مع debug=True سترى صفحة خطأ تفصيلية تعرض:

  1. نوع الاستثناء (ZeroDivisionError).
  2. الرسالة ("division by zero").
  3. مسار الملف ورقم السطر.
  4. تتبّع الاستدعاء (Traceback) كاملاً.
  5. أحياناً Console تفاعلي لفحص المتغيرات.
خطأ قاتل في الإنتاج: ترك debug=True عند النشر يفتح ثغرة حقيقية. صفحة الخطأ التفصيلية تعرض شيفرتك ومتغيراتك ومفاتيحك للمستخدم. عطّله دائماً قبل النشر (debug=False)، أو شغّل عبر خادم إنتاج (gunicorn, uWSGI).
اقرأ الخطأ قبل التخمين: صفحة Flask تعطيك اسم الاستثناء ورقم السطر. اذهب إلى السطر مباشرة. 90% من الحل في قراءة رسالة الخطأ بعناية، لا في تغيير الكود عشوائياً.

حتى مع تطبيق صغير، اعتمد هيكلاً واضحاً من اليوم الأول. سنكبر عليه في المحاضرات القادمة.

التطبيق العملي

المطلوب تطبيق Flask يحتوي أربعة مسارات على الأقل، بينها مسار ديناميكي، مع بيئة افتراضية نظيفة، وتشغيل ناجح من المتصفح.

تطبيق المحاضرة 12

  1. أنشئ مجلد flask-lab12/، ثم انتقل إليه في الطرفية.
  2. أنشئ بيئة افتراضية: python -m venv venv.
  3. فعّلها: venv\Scripts\activate (Windows) أو source venv/bin/activate (macOS / Linux).
  4. ثبّت Flask: pip install flask، وتأكد بـ pip show flask.
  5. أنشئ ملف app.py فيه:
    • المسار / يرجع: "الصفحة الرئيسية لمساق SYBS 2309".
    • المسار /about يرجع: اسمك ورقم الأسبوع.
    • المسار /contact يرجع: بريدك الإلكتروني.
    • المسار /student/<int:sid> يرجع: "المعرّف: N" حيث N هو الرقم الممرّر.
  6. شغّل التطبيق: python app.py أو flask run.
  7. اختبر كل مسار في المتصفح:
    • http://127.0.0.1:5000/
    • http://127.0.0.1:5000/about
    • http://127.0.0.1:5000/contact
    • http://127.0.0.1:5000/student/42
  8. اختبر حالة خطأ مقصودة:
    • افتح /missing → يجب أن ترى صفحة 404.
    • افتح /student/abc → 404 لأن int لا يطابق نصاً.
  9. جرّب debug=True: أضف مساراً جديداً واختبره (بدون إعادة تشغيل يدوي).
  10. جرّب خطأً متعمداً: أضف مسار /boom يعيد 1/0، ولاحظ صفحة Flask التفصيلية.
  11. أنشئ requirements.txt بـpip freeze > requirements.txt.
  12. أرفق app.py، وrequirements.txt، وصورة من الطرفية، وصورة من كل مسار في المتصفح (4 صور على الأقل).
app.py — نموذج البداية PYTHON 
# flask-lab12/app.py
from flask import Flask

app = Flask(__name__)


@app.route("/")
def home():
    return "الصفحة الرئيسية لمساق SYBS 2309"


@app.route("/about")
def about():
    return "عن المساق — الأسبوع 12 — Flask"


@app.route("/contact")
def contact():
    return "البريد: your-email@example.com"


@app.route("/student/<int:sid>")
def student(sid):
    return f"المعرّف: {sid}"


if __name__ == "__main__":
    app.run(debug=True)
معيار الإنجاز: التطبيق يعمل في المتصفح، كل المسارات الأربعة ترجع نصوصها الصحيحة، المسار الديناميكي يقبل الأرقام، debug=True يعمل، والطرفية تعرض "Running on http://127.0.0.1:5000". لا أخطاء حمراء في الطرفية.

أخطاء شائعة ونصائح

نسيان / في المسار

@app.route("about") خطأ. الصواب @app.route("/about"). المسار يجب أن يبدأ بـ/.

تشغيل التطبيق من مجلد خاطئ

flask run يحتاج أن يكون في المجلد الذي فيه app.py (أو استخدام --app). إذا لم يجد الملف، يعطي Could not locate an app.

اسم معامل لا يطابق

في /hello/<name> يجب أن تكون الدالة def hello(name). اختلاف الاسم يُنتج TypeError.

ترك debug=True في الإنتاج

يمكّن مستخدماً من رؤية شيفرتك وبياناتك. عطّله قبل النشر، واستخدم خادم إنتاج.

نسيان templates/

render_template("home.html") يبحث في templates/. إن كان الملف في الجذر أو في مجلد آخر، ستحصل على TemplateNotFound.

تشغيل أكثر من نسخة

إذا كان المنفذ 5000 مشغولاً، يظهر Address already in use. أغلق النسخة القديمة، أو شغّل على app.run(port=5001).

عدم تفعيل البيئة

إن نسيت تفعيل venv، فقد يظهر "Flask غير مثبت" رغم تثبيته داخل البيئة. افتح الطرفية الجديدة دائماً وتأكد من (venv).

استخدام 127.0.0.1 خارج الجهاز

127.0.0.1 يعني "هذا الجهاز فقط". لتعرض التطبيق على شبكتك المحلية، app.run(host="0.0.0.0") — وبحذر، فهو يفتح المنفذ للشبكة.

نصائح ذهبية:
• اقرأ رسالة الخطأ في الطرفية أو صفحة Flask بالكامل.
• ابدأ بأبسط تطبيق (مسار واحد يعيد نصاً)، ثم أضف.
• استخدم أسماء مسارات إنجليزية قصيرة.
• رتّب المشروع من البداية: templates/، static/.
• لا تنسَ requirements.txt.

ملخص المحاضرة

  • Flask إطار عمل خفيف يربط دورات Python بمسارات URL.
  • البيئة الافتراضية venv تعزل مكتبات المشروع عن بقية النظام.
  • الخطوات الثابتة: python -m venv venv، تفعيل، pip install flask.
  • أول تطبيق: app = Flask(__name__)، ثم @app.route("/")، ثم app.run().
  • المسار يُعرَّف بـ@app.route("/path") ويبدأ دائماً بـ/.
  • المعاملات الديناميكية بـ<name> و<int:sid>.
  • الطرق: methods=["GET", "POST"]، وتُقرأ بـrequest.method.
  • الاستجابات: نص، HTML مضمّن، أو render_template (الأفضل).
  • debug=True للتطوير فقط، وللإنتاج عطّله.
  • هيكل المشروع: app.py + templates/ + static/ + requirements.txt.
  • الأخطاء الشائعة: نسيان /، تشغيل من مجلد خاطئ، ترك debug في الإنتاج.

تقييم سريع

1) ما دور إطار العمل مثل Flask، ولماذا لا نكتب الخادم يدوياً؟

لأنه يوفّر استقبال الطلبات، توجيهها إلى المسار المناسب، تحليل البيانات، إعداد الاستجابة، والتعامل مع الأخطاء. كتابة ذلك يدوياً تعني إعادة نفس الكود في كل مشروع، بينما Flask يوفّره جاهزاً لتتركز على منطق تطبيقك.

2) لماذا نستخدم البيئة الافتراضية قبل تثبيت Flask؟

لعزل مكتبات المشروع عن بقية النظام. هذا يمنع تعارض الإصدارات بين المشاريع، ويجعل إعداد أي جهاز آخر ممكناً من requirements.txt. كما يضمن أن تثبيت/تحديث مكتبة هنا لا يؤثر على مشروع آخر.

3) ما الفرق بين @app.route("/about") و@app.route("/hello/<name>")؟

الأول مسار ثابت، يطابق فقط /about. الثاني مسار ديناميكي، يطابق أي اسم، ويُمرّر النص إلى دالة hello(name) كمعامل. النوع يمكن تقييده مثل <int:id>.

4) متى نستخدم GET ومتى نستخدم POST؟

GET لصفحات القراءة والبحث والتصفح؛ بياناته في عنوان URL. POST لإرسال بيانات (تسجيل، دخول، تحديث)؛ بياناته في جسم الطلب، ولا تظهر في العنوان. للبيانات الحساسة: POST مع HTTPS.

5) لماذا لا نضع debug=True في الإنتاج؟

لأنه يعرض صفحات أخطاء تفصيلية تكشف شيفرتك ومتغيراتك ومفاتيحك، وقد تفتح Console تفاعلياً في المتصفح. هذا خطر أمني حقيقي. للإنتاج: debug=False، مع خادم إنتاج مثل gunicorn أو uWSGI.
