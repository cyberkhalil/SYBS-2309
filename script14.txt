[10:00 – 20:00] بنية مشروع Flask الاحترافية
============================================================

دعونا نبدأ بالسؤال الأول: كيف ننظّم مشروع Flask؟

Flask يتوقّع بنية معينة. لو خالفناها، سيبحث عن
الملفات في أماكن خاطئة، ويُعطينا أخطاء غير واضحة.

البنية القياسية:

flask-lab14/
├── app.py
├── requirements.txt
├── templates/
│   ├── base.html
│   ├── home.html
│   └── ...
├── static/
│   ├── css/
│   │   └── style.css
│   └── js/
│       └── main.js
└── venv/       (مستثنى من Git)

شرح كل جزء:

- app.py: نقطة الدخول. فيه كائن التطبيق والمسارات.
- templates/: ملفات Jinja. يبحث فيها Flask تلقائياً.
- static/: ملفات ثابتة. CSS، JS، صور، خطوط.
- requirements.txt: لائحة المكتبات.
- venv/: بيئة افتراضية. لا تُرفع إلى Git.

لماذا هذه البنية؟

أولاً: Flask يفترضها افتراضياً. render_template("home.html")
يبحث في templates/ تحديداً، وليس في الجذر.

ثانياً: الفصل بين "منطق" و"عرض" و"موارد".
- المنطق في app.py.
- العرض في templates/.
- الموارد في static/.

ثالثاً: التوسّع. غداً لو أضفت models/ وblueprints/،
لك أساس نظيف.

احفظوا هذه البنية في أذهانكم. في المشروع النهائي
ستبدؤون بها.

نصيحة عملية: أنشئوا البنية قبل أن تكتبوا أي كود.
mkdir -p templates static/css static/js
ثم ابدأوا بالكتابة. هذا يوفّر إعادة الترتيب لاحقاً.

[20:00 – 35:00] ربط CSS وJS عبر static وurl_for
============================================================

الآن السؤال العملي الأول: كيف نضع CSS الذي كتبناه
في الأسبوع الرابع داخل Flask؟

الجواب: نضع الملف في static/css/style.css، ونربطه في
قالب واحد مشترك (base.html) باستخدام url_for.

تذكّرون ما قلناه في الأسبوع 13 عن url_for. اليوم نطبّقه:

<link rel="stylesheet"
      href="{{ url_for('static', filename='css/style.css') }}">

لاحظوا:
- 'static' كلمة محجوزة في Flask، تعني مجلد الملفات الثابتة.
- filename= مسار الملف داخل static.
- لا تضع 'static/' في filename، لأن url_for يضيفه.

البديل الخاطئ:

<link rel="stylesheet" href="/static/css/style.css">

هذا يعمل غالباً، لكنه ينكسر عند النشر على subpath، مثل:
https://example.com/myapp/static/css/style.css
بدل https://example.com/static/css/style.css.

وفيه مشكلة ثانية:
لو غيّرت اسم المجلد لاحقاً، يجب أن تعدّل كل القوالب.

لذا: url_for دائماً.

الشيء نفسه لـJavaScript:

<script src="{{ url_for('static', filename='js/main.js') }}" defer></script>

defer مهم: السكربت يعمل بعد بناء DOM. بدون defer،
قد يعمل قبل وجود العناصر، فتحدث أخطاء null.

تذكّروا: كود JS الذي كتبتموه في الأسبوع الثامن
يُوضع عادة في static/js/main.js. لكنه يحتاج تعديلاً
بسيطاً ليصبح مناسباً لكل صفحة (لأن base مشترك).

أفضل ممارسة: كل صفحة تضيف ما تحتاجه فقط.
هذا ممكن عبر {% block scripts %}. سنشرحه بعد قليل.

نقطة أخيرة: الملفات الثابتة تُخزَّن مؤقتاً في المتصفح
افتراضياً. عند التعديل، قد تحتاج Ctrl+F5 لتحديثها.
هذا سلوك طبيعي، وليس خطأ.

[35:00 – 50:00] وراثة القوالب مع أنماط متقدمة
============================================================

في المحاضرة 13 شرحنا extends وblock. اليوم نوسّع الفكرة.

القالب base.html الأساسي:

<!DOCTYPE html>
<html lang="ar" dir="rtl">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>{% block title %}تطبيق الملاحظات{% endblock %}</title>
    <link rel="stylesheet"
          href="{{ url_for('static', filename='css/style.css') }}">
    {% block styles %}{% endblock %}
</head>
<body>
    {% include "_header.html" %}
    {% include "_flash.html" %}
    <main>
        {% block content %}{% endblock %}
    </main>
    <footer>...</footer>
    <script src="{{ url_for('static', filename='js/main.js') }}" defer></script>
    {% block scripts %}{% endblock %}
</body>
</html>

لاحظوا إضافتين مهمتين:

1) block styles وblock scripts.
   يتيحان للصفحات إضافة CSS أو JS خاصة بها.
   بدون تكرار في base.

2) include _header.html و_flash.html.
   هذه أجزاء مشتركة صغيرة، نضعها في ملفات خاصة.

لماذا include بدل كتابة الكود مباشرة في base؟

لأن:
- base يبقى أنظف وأسهل في القراءة.
- يمكن إعادة استخدام _header في قوالب أخرى.
- يمكن أن يكون لـ_header منطق خاص (مثل إظهار
  زر تسجيل الدخول إن لم يكن المستخدم مسجلاً).

ملاحظة مهمة على include: المسار "شامل" من templates.
فـ"_header.html" يعني templates/_header.html.
لا تكتب "templates/_header.html".

هناك أيضاً super(). لو أردت في الابن أن تضيف
محتوى فوق محتوى الأب:

{% block scripts %}
    {{ super() }}
    <script src="{{ url_for('static', filename='js/notes.js') }}"></script>
{% endblock %}

هذا يستدعي محتوى block scripts في base، ثم يضيف
سكربت خاص. مفيد جداً.

والآن، سؤال شائع: هل أفضّل extends أم include لكل شيء؟

الجواب:
- extends: للوراثة الكاملة. صفحة ترث من base وتملأ blocks.
- include: لإدراج جزء في موقع معين. مثل ترويسة أو تذييل صغير.

الممارسة الشائعة:
- base.html
- _header.html، _footer.html، _flash.html
- وكل صفحة ترث من base وتدرج _header داخلها.

بهذا تصبح الصفحة = base + blocks + includes. نظيفة.

[50:00 – 65:00] التخزين في الذاكرة
============================================================

الآن نأتي إلى الجزء الذي يجعل تطبيقنا "حياً":
كيف نحفظ البيانات بين الطلبات؟

في المحاضرة 13 كنا نعرض بيانات، لكننا لا نحفظها.
حين يغادر المستخدم الصفحة، تنتهي.

اليوم نضيف الحفظ، بأبسط طريقة: قائمة Python على
مستوى الوحدة (module-level).

notes = []

هذه القائمة موجودة بمجرد تشغيل التطبيق، وتبقى
طوال عمر العملية.

عند إضافة ملاحظة:

notes.append({
    "id": len(notes) + 1,
    "title": title,
    "body": body
})

عند العرض:

return render_template("notes.html", notes=notes)

عند الحذف:

notes = [n for n in notes if n["id"] != note_id]

هذه هي الفكرة. بسيطة، لكن فيها تعليم عميق:
- البيانات state.
- الوحدة تحتفظ بها.
- كل طلب يقرأها/يعدّلها.

مهم أن نفهم حدود هذا الأسلوب:

1) لا تُشارك بين النسخ المتعددة.
   لو شغّلت التطبيق على خادمين، لكل واحد قائمته.
2) تُفقد عند إعادة التشغيل.
3) لا تصلح للكميات الكبيرة.

لكن للتعلّم والمشروع الصغير، مثالية. لأنها:
- تعلّمك دورة حياة البيانات.
- تتيح لك بناء تطبيق كامل بلا تعقيد قواعد البيانات.
- تُظهر لك لماذا نحتاج قاعدة بيانات لاحقاً.

ملاحظة تقنية: عند التعديل على قائمة على مستوى الوحدة
داخل دالة، Python تسمح بـappend وremove مباشرة
(لأنها تعديل على الكائن لا إعادة تعيين). لكن لو
أعدت التعيين: notes = [...] داخل دالة، فأنت تنشئ
متغيراً محلياً. تحتاج global notes.

هذا مثال على "النطاق" الذي شرحناه في الأسبوع 11.

نصيحة: أنشئ دوال مساعدة:
def find_note(note_id): ...
def next_id(): ...

هذا يجعل الكود أنظف وقابلاً للاختبار.

[65:00 – 85:00] أمن المدخلات: التهريب والتحقق
============================================================

الآن نأتي إلى أهم جزء في المحاضرة من الناحية المهنية:
أمن المدخلات.

كل تطبيق ويب حقيقي يقرأ من المستخدم. والمستخدم
ليس دائماً حسناً. بعضهم:
- يكتب HTML و JavaScript.
- يحاول حقن SQL.
- يرفع ملفات خبيثة.
- يُرسل طلبات آلية كثيرة.

نحن نحتاج حماية أساسية. ولا نريد هذه الحماية أن
تُعيق الاستخدام العادي.

ثلاثية الأمان التي نتعلمها اليوم:

1) التهريب (Escaping) عند العرض.
2) التحقق (Validation) في الخادم.
3) HTTPS في الإنتاج.

دعونا نشرح كل واحدة.

التهريب:

Jinja يهرّب تلقائياً كل ما يمرَّر بـ{{ }}.
هذا يعني أن:
{{ note.body }}

لو كان note.body يحتوي على <script>alert(1)</script>،
سيظهر النص حرفياً، ولن يُنفَّذ.

هذا هو السلوك الافتراضي. مثالي.

لكن هناك |safe. لو كتبت:
{{ note.body | safe }}

فسيتم إلغاء التهريب. النص سيُفسَّر كـHTML، والسكربت
سينفّذ. هذه ثغرة XSS.

القاعدة: لا تستخدم |safe على نص المستخدم أبداً.
استخدمها فقط على HTML تكتبه أنت (مثلاً، لو عندك
أجزاء HTML مخزّنة داخل قوالبك)، أو على HTML
مُنقّى بمكتبة مثل Bleach.

التحقق في الخادم:

التحقق هو فحص المدخلات قبل استخدامها. مثل:
- هل العنوان غير فارغ؟
- هل طوله ضمن الحد؟
- هل النص موجود؟
- هل المعرف صالح؟

دالة تحقق بسيطة:

def validate_note(title, body):
    errors = []
    if not title:
        errors.append("العنوان مطلوب.")
    elif len(title) < 3:
        errors.append("العنوان قصير جداً.")
    elif len(title) > 100:
        errors.append("العنوان طويل جداً.")
    if not body:
        errors.append("النص مطلوب.")
    return errors

ثم في المسار:

errors = validate_note(title, body)
if errors:
    for e in errors:
        flash(e, "error")
    return redirect(url_for("note_new"))

التحقق في الخادم ضروري حتى لو تحققنا في JavaScript،
لأن:
- JS يمكن تعطيله.
- يمكن إرسال طلب مباشر بـcurl أو Postman.
- أدوات المطور قابلة للتلاعب.

HTTPS:

في الإنتاج، استخدم HTTPS دائماً. هو يشفّر البيانات
بين المتصفح والخادم. يمنع التجسس (sniffing)
والتلاعب (MITM). محلياً لا نحتاجه، لكن حين ننشر
التطبيق، لا بد منه. مزوّد الاستضافة عادة يوفّره،
أو عبر Let's Encrypt مجاناً.

هذه الثلاثية، مع الالتزام بها، تحمي 80% من الثغرات
الشائعة. الباقي (SQL Injection، CSRF، XSS المتقدم)
يحتاج مكتبات متخصصة لاحقاً (Flask-WTF، csrf tokens،
OWASP قواعد).

[85:00 – 100:00] قراءة التتبعات والسجلات
============================================================

الآن مهارة عملية صغيرة لكنها توفّر ساعات:
قراءة Traceback.

مع debug=True، Flask يعرض صفحة خطأ تفصيلية في المتصفح.
فيها:
- نوع الاستثناء.
- الرسالة.
- السطر الذي فشل (تنقر عليه للسياق).
- Traceback كامل.
- أحياناً console تفاعلي.

في الطرفية، يطبع Flask نفس الشيء بصيغة نصية.

كيف تقرأ Traceback بشكل صحيح؟

1) اقرأ من الأسفل للأعلى.
   السطر الأخير هو الخطأ الأساسي ونوعه.
   ما فوقه تتبّع الاستدعاءات.

2) ابحث عن ملفك.
   في النص، ملف app.py هو ملفك. تخطَّ أسطر Flask
   ومكتباته.

3) اذهب للسطر المذكور.
   ستجد الكود الفعلي الذي فشل.

4) اطبع القيم قبل السطر إذا احتجت.
   console.log في JS لا تعمل هنا. في Python: print().

مثال من التطبيق:

KeyError: 'id'

Traceback:
  File "app.py", line 42, in note_show
    note = find_note(note_id)
  File "app.py", line 18, in find_note
    if n["id"] == note_id:

هذا يعني: في note_show، السطر 42، استدعينا
find_note. في find_note، السطر 18، حاولنا الوصول
لمفتاح "id" وهو غير موجود في n.

السبب المحتمل: لم نضع "id" عند الإضافة. أو نستخدم
مفتاحاً مختلفاً (name بدل id).

الحل: تحقق من بنية القاموس، أو استخدم .get().

أخطاء أخرى شائعة:
- TemplateNotFound: القالب في مجلد خاطئ أو اسمه خطأ.
- JSONDecodeError: نص JSON خاطئ.
- AttributeError: خاصية مفقودة على كائن.
- TypeError: تمرير نوع غير مناسب لدالة.

السجلات (Logs):
Flask يطبع كل طلب في الطرفية:
- GET / HTTP/1.1
- 200 OK
- أو 302 Redirect
- أو 404 Not Found
- أو 500 Internal Server Error

يمكنك معرفة نشاط التطبيق من السجلات. لو رأيت
طلبات كثيرة بسرعة، قد يكون هناك روبوت. لو رأيت 500
متكررة، هناك خطأ في الكود.

في الإنتاج:
- عطّل debug.
- اكتب السجل في ملف.
- لا تُظهر التفاصيل للمستخدم (400/500 عامة).
- راقب السجل بحثاً عن هجمات.

5) app.py:

```python

from flask import (
    Flask, render_template, request,
    redirect, url_for, flash, abort

app = Flask(__name__)
app.secret_key = os.environ.get("SECRET_KEY", "dev-only-change-me")

notes = []


@app.route("/")
def home():
    return render_template("home.html")


@app.route("/notes")
def notes_list():
    return render_template("notes.html", notes=notes)


@app.route("/notes/new", methods=["GET", "POST"])
def note_new():
    if request.method == "POST":
        title = request.form.get("title", "").strip()
        body = request.form.get("body", "").strip()

        if not title:
            flash("العنوان مطلوب.", "error")
            return redirect(url_for("note_new"))
        if len(title) > 100:
            flash("العنوان طويل جداً.", "error")
            return redirect(url_for("note_new"))
        if not body:
            flash("النص مطلوب.", "error")
            return redirect(url_for("note_new"))

        notes.append({
            "id": len(notes) + 1,
            "title": title,
            "body": body
        })
        flash("تمت إضافة الملاحظة.", "success")
        return redirect(url_for("notes_list"))

    return render_template("note_form.html")


@app.route("/notes/<int:note_id>")
def note_show(note_id):
    note = next((n for n in notes if n["id"] == note_id), None)
    if not note:
        abort(404)
    return render_template("note_show.html", note=note)


@app.route("/notes/<int:note_id>/delete", methods=["POST"])
def note_delete(note_id):
    global notes
    before = len(notes)
    notes = [n for n in notes if n["id"] != note_id]
    if len(notes) == before:
        abort(404)
    flash("تم حذف الملاحظة.", "success")
    return redirect(url_for("notes_list"))


if __name__ == "__main__":
    app.run(debug=True)
```
