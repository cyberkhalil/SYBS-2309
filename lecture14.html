بنية مشروع Flask الاحترافية

Flask يتوقّع بنية معينة، ولو خالفناها سيبحث عن الملفات في أماكن خاطئة ويعطينا TemplateNotFound أو 404 لملفات CSS. لذلك نلتزم بالبنية القياسية:

هيكل مشروع Flask TREE 
flask-lab14/
├── app.py
├── requirements.txt
├── templates/
│   ├── base.html
│   ├── home.html
│   ├── notes.html
│   └── note_form.html
├── static/
│   ├── css/
│   │   └── style.css
│   └── js/
│       └── main.js
└── venv/                (مستثنى من Git)
المسار المحتوى كيف يُستخدم في Flask
app.py نقطة الدخول والمسارات يُنفَّذ بـpython app.py أو flask run
templates/ ملفات Jinja / HTML يُستخدم معها render_template
static/ CSS، JS، الصور، الخطوط تُربط عبر url_for('static', filename=...)
requirements.txt لائحة المكتبات والإصدارات pip install -r requirements.txt
venv/ بيئة افتراضية لا تُرفع إلى Git، تُنشأ محلياً
لا تغيّر أسماء templates/ أو static/. لو غيّرت templates إلى views، فلن يجد Flask قوالبك، وستظهر لك TemplateNotFound. يمكن تغييرها برمجياً، لكن لا داعي لذلك الآن.

اعتمد هذه البنية في كل مشروع جديد. ابدأ بالهيكل، ثم أضف الملفات، ولا ترمِ كل شيء في الجذر. عندما يكبر المشروع، ستحتاج إلى إضافة blueprints/ وmodels/ وأشياء أخرى، وسيكون لديك أساس نظيف تتوسع عليه.

ربط CSS و JS عبر static وurl_for

أسهل خطأ يقع فيه المبتدئ عند الدمج هو كتابة مسارات يدوية، مثل <link href="/static/css/style.css">. هذا يعمل في بيئة محلية بسيطة، لكنه ينكسر عند النشر على مسار فرعي، أو عند تغيير الإعدادات. الحل الصحيح هو url_for.

templates/base.html HTML + JINJA 
<!DOCTYPE html>
<html lang="ar" dir="rtl">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>{% block title %}تطبيق الملاحظات{% endblock %}</title>

    <!-- ربط CSS من static/css/style.css -->
    <link rel="stylesheet"
          href="{{ url_for('static', filename='css/style.css') }}">
</head>
<body>
    <header class="site-header">
        <h1>تطبيق الملاحظات</h1>
        <nav>
            <a href="{{ url_for('home') }}">الرئيسية</a>
            <a href="{{ url_for('notes_list') }}">الملاحظات</a>
            <a href="{{ url_for('note_new') }}">ملاحظة جديدة</a>
        </nav>
    </header>

    <main>
        {# رسائل Flash (تابع من المحاضرة 13) #}
        {% with messages = get_flashed_messages(with_categories=true) %}
            {% if messages %}
                <ul class="flash-list">
                {% for category, msg in messages %}
                    <li class="flash flash-{{ category }}" role="alert">{{ msg }}</li>
                {% endfor %}
                </ul>
            {% endif %}
        {% endwith %}

        {% block content %}{% endblock %}
    </main>

    <footer class="site-footer">
        <p>SYBS 2309 — تصميم وبرمجة الويب</p>
    </footer>

    <!-- ربط JS من static/js/main.js -->
    <script src="{{ url_for('static', filename='js/main.js') }}" defer></script>
</body>
</html>

الملفات الثابتة

  • تُوضع في static/
  • تُقدَّم مباشرة للمتصفح
  • لا تمر عبر Jinja
  • يمكن تخزينها مؤقتاً عبر HTTP headers

url_for

  • url_for('static', filename='...') للملفات
  • url_for('home') لمسار
  • url_for('student', sid=42) مع معامل
  • يعمل مهما تغيّر التطبيق

تصحيح

  • لو لم يوجد الملف: 404 في Network
  • لو اسم الملف خاطئ: تحقق من الحالة
  • لو المسار غلط: افتح Network
  • لا تكتب paths يدوية

لا تكرر

  • لا تكرر رابط CSS في كل قالب
  • لا تكرر سكربت JS

  • استخدم blocks لملفات خاصة لاحقاً

block

  • مكان قابل للاستبدال في الأب
  • الابن يملأه أو يتركه فارغاً
  • يمكن أن يحتوي محتوى افتراضياً
  • لا يتكرر بين القوالب

include

  • يُدرج ملفاً في المكان
  • لا يعدّل الأب
  • مفيد للأجزاء الصغيرة المتكررة
  • مثل الترويسة أو رسائل Flash

super()

  • استدعاء محتوى الأب من الابن
  • مثال: {{ super() }}
  • مفيد عند إضافة سكربت
  • أو عند تمديد block

تحذير

  • extends أول سطر في الابن
  • لا تنسَ endblock
  • لا تكتب DOCTYPE في الابن
  • احترم مستوى العنوان

التخزين في الذاكرة

حتى الآن تطبيقنا لا يحفظ شيئاً بعد إغلاق الطلب. في هذه المحاضرة سنستخدم حيلة بسيطة: متغير Python على مستوى الوحدة (module) يبقى حياً طوال عمر العملية. هذا يسمح لنا ببناء تطبيق يُضيف ويقرأ ويحذف.

حدود هذا الأسلوب: الذاكرة ليست قاعدة بيانات. عند إعادة تشغيل الخادم، تضيع البيانات. وعند العمل مع أكثر من نسخة من التطبيق (production)، كل نسخة لها ذاكرتها. لكن للتعلّم والمشروع الصغير، هذا مثالي — يعلّمك دورة حياة البيانات دون تعقيد قواعد البيانات.
app.py — هيكل البيانات في الذاكرة PYTHON 
# قائمة الملاحظات — "قاعدة بيانات مؤقتة"
notes = []


def next_id():
    """يولّد معرفاً تسلسلياً بسيطاً."""
    return len(notes) + 1


def find_note(note_id):
    """يبحث عن ملاحظة بالمعرّف. يعيد None إذا لم يجد."""
    for n in notes:
        if n["id"] == note_id:
            return n
    return None
app.py — مسارات القائمة والإضافة PYTHON 
from flask import (
    Flask, render_template, request,
    redirect, url_for, flash,
    abort, session
)
import os

app = Flask(__name__)
app.secret_key = os.environ.get("SECRET_KEY", "dev-secret-change-me")

notes = []


@app.route("/notes")
def notes_list():
    return render_template("notes.html", notes=notes)


@app.route("/notes/new", methods=["GET", "POST"])
def note_new():
    if request.method == "POST":
        title = request.form.get("title", "").strip()
        body = request.form.get("body", "").strip()

        # تحقق
        if not title:
            flash("العنوان مطلوب.", "error")
            return redirect(url_for("note_new"))
        if len(title) > 100:
            flash("العنوان طويل جداً.", "error")
            return redirect(url_for("note_new"))
        if not body:
            flash("النص مطلوب.", "error")
            return redirect(url_for("note_new"))

        # إضافة
        notes.append({
            "id": len(notes) + 1,
            "title": title,
            "body": body
        })
        flash("تمت إضافة الملاحظة.", "success")
        return redirect(url_for("notes_list"))

    return render_template("note_form.html")


@app.route("/notes/")
def note_show(note_id):
    note = find_note(note_id)
    if not note:
        abort(404)
    return render_template("note_show.html", note=note)


@app.route("/notes//delete", methods=["POST"])
def note_delete(note_id):
    note = find_note(note_id)
    if not note:
        abort(404)
    notes.remove(note)
    flash("تم حذف الملاحظة.", "success")
    return redirect(url_for("notes_list"))

أمن المدخلات: التهريب والتحقق

تطبيق ويب يقرأ من المستخدم، ولا يعرف نواياه. قد يكتب نصاً عادياً، وقد يكتب هجوماً. أمن المدخلات هو فن التعامل مع الاثنين دون أن ينكسر التطبيق.

التهريب (Escaping) — خط الدفاع الأول

التهريب يعني تحويل الرموز الخاصة في النص إلى صيغة آمنة قبل عرضها. مثلاً، < تصبح &lt;، فلا تُفسَّر كوسم HTML.

الفرق بين الآمن والخطر JINJA / HTML 
{# آمن — Jinja يهرّب تلقائياً #}
<p>{{ note.body }}</p>

{# خطر — يُظهر HTML كما هو #}
<p>{{ note.body | safe }}</p>

Jinja يهرّب تلقائياً كل ما يمرَّر بأقواس {{ }}. هذا هو السلوك الافتراضي، وهو صديقك. لا تُلغِه إلا إذا كنت تعرض HTML كتبته أنت، وليس المستخدم.

مثال على هجوم XSS: لو سمحت للمستخدم بحفظ <script>alert('XSS')</script> في ملاحظة، ثم عرضتها بـ|safe، فسيُنفَّذ السكربت في متصفح كل زائر. هذا هو Cross-Site Scripting. مع {{ note.body }} فقط، يظهر النص حرفياً ولا ينفَّذ.

التحقق في الخادم — خط الدفاع الثاني

التهريب يحمي العرض. التحقق يحمي المنطق. لا يُغني أحدهما عن الآخر. نتحقق من:

دالة تحقق بسيطة PYTHON 
def validate_note(title, body):
    """تُرجع قائمة أخطاء. فارغة = صحيح."""
    errors = []

    if not title:
        errors.append("العنوان مطلوب.")
    elif len(title) < 3:
        errors.append("العنوان قصير جداً (3 أحرف على الأقل).")
    elif len(title) > 100:
        errors.append("العنوان طويل جداً (100 حرف كحد أقصى).")

    if not body:
        errors.append("النص مطلوب.")
    elif len(body) > 5000:
        errors.append("النص طويل جداً (5000 حرف كحد أقصى).")

    return errors

تحقق دلالي

  • الوجود: الحقل غير فارغ
  • الطول: الأقل والأقصى
  • النوع: رقم / بريد / تاريخ
  • المدى: 1–100 مثلاً

تحقق منطقي

  • البريد غير مستخدم
  • المستخدم له صلاحية
  • المعرّف موجود فعلاً
  • لا يمكن حذف غير موجود

HTTPS

  • يشفّر البيانات في الطريق
  • يمنع sniffing
  • ضروري في الإنتاج
  • محلياً غير مطلوب

لا تعتمد على

  • تحقق HTML5
  • تحقق JavaScript
  • أدوات المتصفح
  • الشبكة الآمنة وحدها
ثلاثية الأمان الأساسية:
1. تهريب عند العرض بـ{{ }}.
2. تحقق في الخادم قبل الاستخدام.
3. HTTPS عند النشر.
ثلاثتها معاً تصنع طبقات دفاع، لا تعتمد على واحدة.

قراءة التتبعات (Tracebacks) والسجلات

في التطوير، debug=True يعرض صفحة خطأ تفصيلية في المتصفح. هذه الصفحة هي أفضل صديق لك، لأنها تخبرك بالضبط بما حدث:

  1. نوع الاستثناء (ZeroDivisionError، KeyError…).
  2. الرسالة الكاملة.
  3. المسار والسطر في ملفك.
  4. تسلسل الاستدعاء (Traceback).
  5. أحياناً Console تفاعلي لفحص متغيرات.

في الطرفية، يطبع Flask نفس المعلومات بصيغة نصية. ستراها تحت السطر الذي يبدأ بـ[ERROR] أو Traceback (most recent call last):.

كيف تقرأ Traceback

  • اقرأ من الأسفل للأعلى
  • السطر الأخير = الخطأ الأساسي
  • ابحث عن ملفك (app.py)
  • اذهب للسطر المذكور

أخطاء شائعة

  • TemplateNotFound — القالب في مجلد خاطئ
  • KeyError — مفتاح مفقود في request.form
  • TypeError — نوع غير مناسب
  • AttributeError — خاصية مفقودة

السجلات (Logs)

  • Flask يطبع كل طلب
  • GET / ثانية
  • رمز الحالة (200، 302، 404، 500)
  • يمكن قراءتها لمعرفة النشاط

في الإنتاج

  • عطّل debug
  • السجل يُكتب في ملف
  • لا تُظهر التفاصيل للمستخدم
  • الخطأ يُعالَج داخلياً
قاعدة ذهبية: لا تحاول "تخمين" الخطأ، اقرأ Traceback. 95% من الوقت، الجواب موجود في السطر الأول بعد اسم الملف. الخطأ في السطور النصية ليس مؤشراً على تعقيد، بل على تهاون.

app.py — الهيكل الكامل للبداية PYTHON 
import os
from flask import (
    Flask, render_template, request,
    redirect, url_for, flash, abort
)

app = Flask(__name__)
app.secret_key = os.environ.get("SECRET_KEY", "dev-only-change-me")

# "قاعدة بيانات مؤقتة" — قائمة في الذاكرة
notes = []


@app.route("/")
def home():
    return render_template("home.html")


@app.route("/notes")
def notes_list():
    return render_template("notes.html", notes=notes)


@app.route("/notes/new", methods=["GET", "POST"])
def note_new():
    if request.method == "POST":
        title = request.form.get("title", "").strip()
        body = request.form.get("body", "").strip()

        if not title:
            flash("العنوان مطلوب.", "error")
            return redirect(url_for("note_new"))
        if len(title) > 100:
            flash("العنوان طويل جداً.", "error")
            return redirect(url_for("note_new"))
        if not body:
            flash("النص مطلوب.", "error")
            return redirect(url_for("note_new"))

        notes.append({
            "id": len(notes) + 1,
            "title": title,
            "body": body
        })
        flash("تمت إضافة الملاحظة.", "success")
        return redirect(url_for("notes_list"))

    return render_template("note_form.html")


@app.route("/notes/")
def note_show(note_id):
    note = next((n for n in notes if n["id"] == note_id), None)
    if not note:
        abort(404)
    return render_template("note_show.html", note=note)


@app.route("/notes//delete", methods=["POST"])
def note_delete(note_id):
    global notes
    before = len(notes)
    notes = [n for n in notes if n["id"] != note_id]
    if len(notes) == before:
        abort(404)
    flash("تم حذف الملاحظة.", "success")
    return redirect(url_for("notes_list"))


if __name__ == "__main__":
    app.run(debug=True)

معيار الإنجاز: التطبيق يعمل كاملاً، قائمة الملاحظات تُعرض وتُضاف وتُحذف، المسار 404 يعمل، رسائل Flash تظهر في الترويسة (بعد الـredirect) عبر base.html، ومحاولة إدخال HTML تُعرض كنص حرفي. هذا هو المشروع المصغّر الذي يمهد للمشروع النهائي.

أخطاء شائعة ونصائح

نسيان مجلد templates

render_template("home.html") يبحث في templates/ فقط. لو وضعت الملف في الجذر، ستحصل على TemplateNotFound.

مسار CSS يدوي

href="/static/..." أو href="static/..." قد يعمل، لكنه ينكسر عند النشر. استخدم url_for('static', filename=...) دائماً.

نسيان تعريف notes = []

لو عرّفت notes داخل دالة، فستنشئ قائمة جديدة في كل طلب. عرّفها على مستوى الوحدة (module) خارج الدوال.

مفتاح مفقود في request.form

request.form["title"] يرفع KeyError إذا كان الحقل غائباً. استخدم .get("title", "") دائماً.

استخدام |safe

{{ note.body | safe }} على نص المستخدم = XSS. احذف |safe ما لم تكن تعرض HTML تكتبه أنت.

تحديث يعيد POST

إذا عرضت صفحة النتيجة مباشرة بعد POST، فالتحديث يُعيد الإرسال. استخدم نمط PRG: flash + redirect.

حذف بـGET

رابط <a href="/delete"> للحذف يخالف قواعد HTTP ويجعل الزحف خطراً. استخدم <form method="post">.

جلسة ملاحظات مشتركة

قائمة notes مشتركة بين كل الزوار. هذا مقبول للتدريب. للإنتاج، استخدم قاعدة بيانات وجلسات مستخدم.

نصائح ذهبية:
• رتّب ملفاتك بدقة قبل الكتابة، لا بعدها.
• استخدم url_for لكل ما هو داخلي.
• التحقق في الخادم مبدأ ليس اختياراً.
• لا تستخدم |safe على نص مستخدم.
• اقرأ Traceback قبل التخمين.
• استخدم PRG: Flash + Redirect بعد POST.

ملخص المحاضرة

  • بنية Flask: app.py + templates/ + static/ + requirements.txt.
  • الملفات الثابتة في static/ وتُربط عبر url_for('static', filename='...').
  • المسارات تُربط عبر url_for('endpoint') — لا مسارات يدوية.
  • الوراثة بـextends + block + include.
  • التخزين في الذاكرة عبر قائمة على مستوى الوحدة — تعليمي، لا إنتاجي.
  • التحقق من المدخلات في الخادم إلزامي، لا يكفي تحقق الواجهة.
  • Jinja يهرّب تلقائياً؛ |safe خطر على نص المستخدم.
  • HTTPS ضروري في الإنتاج لحماية البيانات في الطريق.
  • قراءة Traceback: من الأسفل للأعلى، اذهب مباشرة للملف والسطر.
  • PRG (Post/Redirect/Get) يمنع إعادة الإرسال عند تحديث الصفحة.
  • هذه المحاضرة تمهد للمشروع النهائي — طبّقها بعناية.

تقييم سريع

1) لماذا نستخدم url_for بدل كتابة المسارات اليدوية؟

لأنه يولّد المسار الصحيح تلقائياً بناءً على اسم الدالة أو الملف، ويعمل مهما تغيّر المسار الجذري أو إعدادات النشر. المسارات اليدوية تنكسر عند النشر على مسار فرعي.

2) ما وظيفة templates/ وstatic/ في Flask؟

templates/ يحوي ملفات Jinja/HTML التي تُعالَج عبر render_template. static/ يحوي CSS وJS والصور التي تُقدَّم مباشرة للمتصفح دون معالجة، وتُربط عبر url_for('static', filename=...).

3) لماذا لا نستخدم |safe على نص المستخدم؟

لأنه يعطّل التهريب التلقائي في Jinja، فيُعرض النص كـHTML حقيقي. لو كتب المستخدم <script>alert(...)</script>، فسيُنفَّذ في متصفح كل زائر — ثغرة XSS.

4) ما الفرق بين التخزين في الذاكرة وقاعدة البيانات؟

الذاكرة في قائمة Python تُفقد عند إعادة التشغيل، ولا تُشارك بين النسخ المتعددة من التطبيق. قاعدة البيانات تحفظ البيانات بشكل دائم، وتُشارك بين النسخ، وتناسب الإنتاج. التخزين في الذاكرة تعليمي ومشروع صغير فقط.

5) لماذا نستخدم نمط Post/Redirect/Get (PRG)؟

لأن عرض نتيجة POST مباشرة يجعل تحديث الصفحة يُعيد إرسال الطلب. مع PRG: بعد POST نعمل redirect إلى صفحة GET، فلا يمكن للمستخدم إعادة POST بتحديث الصفحة. flash تنقل رسالة النجاح إلى الطلب التالي.

6) كيف تقرأ Traceback بشكل صحيح؟

اقرأ من الأسفل للأعلى. السطر الأخير يعطي نوع الخطأ ورسالته. في الأعلى، تتبّع الاستدعاءات. ابحث عن الملف الخاص بك (app.py) واذهب للسطر المذكور. غالباً الخطأ واضح في أول سطر يشير لملفك.
